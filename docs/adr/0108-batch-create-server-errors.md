# ADR-0108：建立批次時收到 5xx

## 脈絡

ADR-0107 第 8 項把建立批次的結果分成兩種：有收到回應就照實記下，失敗代表沒有建立，單位放回佇列；沒有收到回應時不知道有沒有建立，留著意圖紀錄。brief 019 照這個寫，429 與 5xx 都原地重試，重試用完就放棄意圖紀錄。

審查 PR 53 時發現，5xx 是伺服器出錯，不保證出錯之前沒有建立批次。萬一建立了，每重試一次就多一批、多付一次。原本那批的意圖已經放棄，不會收回，也不會刪除遠端資料，違反 ADR-0033 第 2 項。

維護者在 2026-11-02 審查 PR 53 時，從問題介面選了「只有 4xx 算沒建立」。

## 決定

1. 修改 ADR-0107 第 8 項：建立批次時收到 4xx 才代表沒有建立，意圖標成放棄，單位放回佇列。429 這類 4xx 照舊原地重試，次數與退避跟 ADR-0107 第 12 項相同。
2. 收到 5xx 跟沒有收到回應一樣，不知道有沒有建立：不重試，留著意圖紀錄並停下，回報 `translate.provider_failed`。下次執行照 ADR-0107 第 9 項從 `list` 認回，沒有候選就當成沒有送出，單位放回佇列重送。
3. 查詢、下載結果、取消、刪除、列出不受影響，照 ADR-0107 第 12 項重試 5xx。

## 後果

建立時遇到 5xx，這次執行就停下，要再執行一次才會認回或重送，不會在原地等伺服器恢復。認回依賴 H-17，H-17 仍是假說，要等 brief 022 之後的真實請求確認。伺服器其實沒有建立時，下次執行多查一次 `list`，確認沒有候選才重送。

## 替代方案

**5xx 照舊原地重試**：伺服器其實已經建立時，每重試一次就多付一批，原本那批也不會收回或刪除；**5xx 不重試，但當成沒有建立**：伺服器其實已經建立時，下次執行會再送同樣的單位，一樣多付一批，原本那批也不會收回或刪除。
